## 2. 감점이 큰 약점 상위 5개 (감점 크기 순)

### W1. 대표 차별점인 "음악+조명 공간 연출"이 기본 설정에서는 주행 중에 동작하지 않는데, 기획서와 화면은 동작하는 것처럼 보여 줌 (차량특화성·신뢰도 동시 감점)

- 3절 "폰과 비교했을 때 차에서만 되는 것" 2번은 "음악과 조명이 동기화된 공간 연출", 시나리오 ①은 "조명은 딥블루로 4초에 걸쳐 바뀝니다", 시나리오 ③은 "조명은 핑크와 오렌지 그라데이션으로 바뀝니다"라고 씁니다. 그런데 5-3에서는 "**주행 중 조명 변경은 기본 보류**"라고 하고, 코드 테스트(`ambient is held while driving and applied after parking`)도 주행 중 조명이 `null`임을 보장합니다.
- 주행 화면 시안 6장 가운데 4장(`drive-heavyrain-allow`, `drive-tunnel-allow`, `drive-jam-allow`, `drive-finale-allow`)은 **기본값이 아닌 허용 모드**로 찍은 것입니다. 이 화면에는 "실내 조명은 정차 시 적용" 배지가 없고 글로우가 강합니다. 심사위원은 이 차이를 알 수 없습니다.
- 그 결과 기본 설정의 **터널 장면은 아무 일도 하지 않습니다**. 곡 유지, 침묵, 조명 보류가 겹치기 때문입니다. 기획서가 "구현 완료"라고 강조한 터널 기능이 실제 사용자에게는 보이지 않습니다.
- **고칠 것**
  1. 3절 2번을 "정차·충전·도착 순간에는 조명까지 포함한 공간 연출, 주행 중에는 음악과 화면 무드 색으로 연출(플랫폼이 허용하면 주행 중 조명까지 확장)"으로 바꿉니다. 시나리오 ①의 3번 문장도 "곡은 어쿠스틱으로 넘어가고, 화면 무드 색이 딥블루로 바뀝니다(조명은 정차 시)"로 고칩니다.
  2. 시안의 `-allow` 4장에 "주행 중 조명 허용 시(설정)" 캡션을 달거나, 기본값 화면으로 다시 찍습니다.
  3. 차량특화성 논리의 중심을 **주행 중에도 확실히 동작하는 것**으로 옮깁니다. 즉 와이퍼·하향등·크루즈·주행모드로 입력 없이 장면을 감지하는 것, 연속 주행 시간에 따른 휴식 안내, NaviHelper 경유지 추가입니다. 조명은 정차 순간을 꾸미는 연출(도착 피날레와 주차 순간 조명 클라이맥스)로 재정의합니다.
  4. 11/09 전에 에뮬레이터 D단에서 `setAmbientLightBrightnessColor` 호출을 직접 시험하고, 그 결과(허용/거부)를 기획서 5-3에 한 줄로 적습니다. 답변을 기다리는 것보다 이 한 줄이 설득력이 큽니다.

### W2. 사업성: 같은 앱마켓에 멜론이 있는데 자체 로열티프리 음원으로 경쟁하는 구조 (사업성 감점)

- 근거 문서에는 "플레오스 커넥트 앱 마켓에 멜론·카카오내비가 새로 입점함(2026-09-07)"이 있지만 기획서에는 없습니다. 심사위원이 가장 먼저 물을 질문입니다. "내 멜론 플레이리스트는 어떻게 되나요?"
- 현재 카탈로그는 44곡이 모두 `artist: "MoodLab Sample"`, `source: ""`, `license: "placeholder"`입니다(`core/src/main/resources/catalog/tracks.json`). 시안에도 "MoodLab Sample"이 그대로 보입니다.
- 6절 수익 모델 1번 "스트리밍 제휴: 신규 구독 전환 수수료"는 제휴 상대가 MooDrive를 쓸 이유(상대가 얻는 것)를 설명하지 않습니다.
- **고칠 것**
  1. 6절 첫머리에 포지셔닝 한 문장을 넣습니다. "MooDrive는 음원 앱이 아니라 **차량 상황 엔진**이며, B2C 데모는 자체 음원으로 하고 상용화는 멜론·지니 같은 Pleos 입점 음원 앱에 상황 신호와 무드 좌표를 제공하는 B2B2C 레이어로 갑니다."
  2. 파트너가 얻는 가치를 수치 가설로 적습니다. 예: "차량 내 세션 길이 +X%, 스킵률 −Y%를 파일럿 KPI로 제시". 가정치라고 밝히되 측정 방법(스킵률 = 30초 내 스킵 / 재생 수)까지 적습니다.
  3. MAU 산식의 방문율 30%, 설치율 5%, 활성률 30%에 각각 비교 근거를 하나씩 붙입니다. 예: 근거 문서의 "앱마켓 국내 앱 18종" → 초기 생태계라 노출 기회가 큼. 근거가 없으면 보수·기준·낙관 3개 시나리오로 범위를 제시합니다.
  4. "(가정치, 근거 보강 필요)"라는 내부 메모 문구는 제출본에서 지우고 "가정"으로만 표기합니다.

### W3. 기술활용성: "구현 완료"라고 썼지만 Pleos SDK 연동은 0%, 핵심 신호 3개의 입수 여부도 미확인 (기술활용성 감점, Q&A 위험)

- 앱 모듈 상태: `PleosVehicleSignalSource.snapshots = emptyFlow()`, `PleosAmbientController.apply()`는 로그만 출력, TTS는 `android.speech.tts.TextToSpeech`(Pleos TTS 아님), 음원 재생은 "TODO: Media3 ExoPlayer로 교체", 휴게소 경유는 "TODO: NaviHelper로 근처 휴게소 검색".
- 엔진이 의존하는 신호 중 확인되지 않은 것들:
  - **기어**(`isDriving`, 주차, 드라이브 카드, 조명 보류가 모두 기어에 의존): Vehicle 19개 도메인 목록에 Gear가 없습니다. 어댑터에도 "어느 도메인에서 오는지 확인"이라는 TODO만 있고, 기획서 SDK 표에는 아예 빠져 있습니다.
  - **와이퍼 강도**: STATUS.md는 "Wiper API는 State/Switch만 있음. 강도 단계 값은 미확인"이라고 적었습니다. 그런데 기획서 F1 표는 "OFF→INT→HIGH"를 전제로 하고, 폭우 장면과 그 안전 멘트는 HIGH 단계가 있어야만 성립합니다.
  - **NaviHelper 남은 시간·정체**: 부록 A에서 ⚠️ 상태입니다. 정체 장면과 F4 피날레가 모두 여기에 걸려 있습니다.
- **고칠 것**
  1. 5-4 "구현 현황"을 "엔진 로직(순수 Kotlin, 테스트 34개)은 완료, 차량 신호는 시나리오 재생으로 대체, Pleos SDK 연결은 11/04~11/09 진행"으로 정직하게 나눠 씁니다. 심사위원은 GitHub를 열어 볼 수 있으므로 과장은 가산점을 오히려 깎습니다.
  2. 부록 A를 신호별 **대체 경로 표**로 바꿉니다. 예: 와이퍼 강도 미지원 → 와이퍼 ON 지속 시간과 날씨 API 강수량으로 폭우 판정. 기어 미지원 → FusedLocation speed > 5km/h를 주행으로 판정. 정체 미지원 → speed 이동평균으로 판정.
  3. 1차 제출 전에 최소한 Wiper·LowBeam·DrivingMode 구독과 Light set 시도를 Virtual Console로 움직이는 30초 영상을 만들어 7절 시연 영상에 넣습니다. "실제 SDK 신호로 장면이 바뀐다"는 장면이 기술활용성 점수를 가장 크게 올립니다.

### W4. 경쟁 비교가 근거 문서와 어긋나고, 가장 위협적인 경쟁자 둘이 빠짐 (창의성·신뢰도 감점)

- 기획서는 메르세데스 ENERGIZING을 "차량 신호 기반 상황 감지는 없음"이라고 적었습니다. 하지만 근거 문서는 "COACH는 Garmin 웨어러블의 스트레스·심박변이 데이터와 **교통 상황·날씨·주행 시간**을 바탕으로 프로그램을 추천"한다고 씁니다. 자기 근거와 모순되는 문장입니다.
- 비교표에 없는 것:
  - **Gleo AI**: Pleos Connect 기본 탑재 LLM 비서로, "주행 맥락과 차량 상태를 반영"합니다(근거 문서 5절). 심사위원은 "Gleo가 '비 오니까 차분한 노래 틀어 줘'를 하면 끝 아닌가요?"라고 물을 것입니다.
  - **멜론(Pleos 입점)**, **Tesla Light Sync**(음악과 조명 동기화, 근거 문서 4절), **Climatune·Songza**(날씨 기반 음악의 선례).
- **고칠 것**
  1. ENERGIZING 행을 "COACH가 교통·날씨·주행 시간으로 웰니스 프로그램을 **추천**하지만 실행은 사용자가 승인함. 10분 단위 프로그램이고 음악 큐레이션은 제한적"으로 고칩니다.
  2. Gleo AI 행을 추가하고 차이를 한 줄로 씁니다. "Gleo는 **요청을 받아야** 움직이고, MooDrive는 **요청 없이** 장면 변화를 감지해 곡 전환, 피날레 큐, 도착 연출까지 이어지는 흐름을 설계함. 장기적으로 Gleo에 MooDrive 장면 신호를 제공하는 연동도 가능."
  3. 표 아래 인용문을 MooDrive만의 차이 3가지로 줄입니다. (1) 무입력 장면 감지, (2) 남은 시간에 맞춘 경로 앨범과 피날레, (3) 터널·비 그침처럼 장면이 바뀌는 순간에 맞춘 짧은 멘트.

### W5. 안전 기능의 논리가 근거와 코드 모두와 어긋남 (차량특화성·창의성 감점, PT 위험)

- **각성 부스트가 심야(23~05시)에만 켜짐**: `ContextEngine.isLateNight`. 그런데 기획서가 근거로 든 한국도로공사 권고는 시간대와 무관하게 "2시간 이상 연속 운전 시 휴식"입니다. 낮 3시간 운전에는 휴식 안내가 없습니다.
- **각성 부스트 무드 = 에너지 0.9**: 근거 문서 3-2는 빠른 템포가 시뮬레이터 주행에서 속도·신호위반을 늘린다고 정리하고, "템포 상한 110 BPM" 같은 설계 시사점까지 적었습니다. 하지만 코드의 `Track.bpm` 필드는 어디에서도 쓰이지 않고, 기획서에도 템포 상한이 없습니다. 스포츠 모드(에너지 0.8)도 마찬가지입니다.
- **시나리오 ②의 "내기순환이 계속되고 있습니다"**: 엔진에는 내기순환 입력이 없습니다(`VehicleSnapshot`에 필드 없음). 근거 문서에 "히터·환기 부족에 따른 CO₂ 상승"이 졸음 사망 증가 원인으로 나와 있어 좋은 소재인데, 활용하지 않았습니다.
- **"화면을 보지 않는 인터랙션이 기본"**: 시안의 음성 입력은 '말하기' 터치 버튼입니다. 근거 문서의 TRL 연구는 **음성 조작도 반응시간을 30~36% 늘린다**고 했는데, 기획서는 터치 57%만 인용했습니다.
- **고칠 것**
  1. F1 표의 각성 부스트 행을 "연속 주행 2시간 이상(시간대 무관) → 휴식 제안. 심야(23~05시)에는 추가로 각성 선곡"으로 바꾸고 코드도 맞춥니다.
  2. 5-3 안전 원칙에 "비·폭우·정체 구간 템포 상한 110 BPM, 각성 부스트는 BPM 상한 대신 **선호 장르** 우선(근거: 직접 고른 음악이 경계 유지에 유리, 2022 프랑스 연구)"을 추가하고, `Curator`에 bpm 필터를 넣습니다.
  3. 내기순환 30분 이상 지속 시 "환기할까요?" 멘트를 추가합니다(`getHvacRecirculationState`는 이미 SDK 표에 있음). 이렇게 하면 시나리오 ②의 문장이 사실이 되고, 폰으로는 할 수 없는 기능이 하나 늘어납니다.
  4. 음성 시작 방식을 명시합니다. 스티어링휠 음성 버튼을 쓸 수 있는지 확인하고, 안 되면 "앱은 기본적으로 말을 걸지 않고, 사용자가 꼭 해야 하는 조작은 0회"라는 쪽으로 논리를 다시 세웁니다. TRL 인용에는 음성 수치(36%)도 함께 적어 "그래서 음성마저 줄이는 **무입력**이 목표"로 연결하면 오히려 근거가 강해집니다.

7. **"졸음 안내는 왜 밤 11시~새벽 5시에만 하나요? 낮에 3시간 운전하면요?"**
8. **"곡의 에너지·밝음 값은 누가 어떻게 매기나요? 상용 카탈로그 수백만 곡은요?"** 태깅 가이드 파일이 없고, 자동 태깅 계획(오디오 특징 추출, 파트너 메타데이터)도 없습니다.
9. **"TTS 멘트가 나올 때 음악은 어떻게 되나요(덕킹)? 내비 음성 안내와 겹치면요?"** 부록 A에 ⚠️만 있고 정책이 없습니다. 내비 안내와 겹칠 때의 우선순위는 언급조차 없습니다.
10. **"시동 걸면 자동 실행된다고 하셨는데, 플랫폼이 허용하나요? 허용되지 않으면 D30 25%의 근거는요?"**
11. **"MAU 9만 명 산식의 설치율 5%, 활성률 30%는 어디서 나온 숫자인가요?"**
12. **"동승자가 음악을 바꾸고 싶으면요? 사용자가 직접 고른 곡과 자동 전환이 충돌하면요?"** 수동 재생 우선이나 자동 전환 일시정지 같은 규칙이 없습니다.
13. **"오프라인(터널·산간)에서 날씨 API가 끊기면요?"** 음원이 번들이라 재생은 되겠지만 기획서에 언급이 없습니다.

## 5. 기획서 형식 문제

- **분량**: 마크다운 약 22KB이고, 8개 필수 항목 뒤에 부록 A~D가 붙어 있습니다. 접수양식은 DOCX이므로 ASCII 아키텍처 다이어그램(5-1)은 글꼴이 바뀌면 깨지고, 표 10여 개도 양식 칸에 맞지 않을 수 있습니다. 5-1은 이미지로 바꾸는 것을 권합니다.
- **부록 처리**: 부록 B(답변 대기 질문 6개)와 D(리스크)는 "핵심 기능이 플랫폼 허용 여부에 달려 있다"는 인상을 줍니다. 리스크와 대응은 5절에 3줄로 줄여 넣고, 상세 내용은 GitHub `docs/`로 옮깁니다. 부록 C(일정)는 5-4와 겹치고 서로 모순되므로 하나로 합칩니다.
- **1. 한 줄 소개**: 한 문장이지만 길고, "창밖"과 "날씨"가 실제 구현(차량 신호 기반)과 어긋납니다. 예시: "와이퍼·전조등·내비 같은 차량 신호로 비, 터널, 정체, 도착을 알아채 아무 조작 없이 음악과 실내 무드를 바꿔 주는 인카 DJ."
- **2. 기획 배경**: 구조는 좋습니다(불편한 순간 → 왜 차여야 하나 → 숫자 → 비교). 다만 각주 [^3], [^6] 번호가 비어 있고, 2017년 자료에 연도를 적지 않았고, 비교표에 Gleo·멜론이 빠졌습니다.
- **3. 주요 기능 및 차량 특화 요소**: 기능 표와 매핑 표는 명확합니다. 그러나 "F1 판정 안정화 (구현 완료)"는 기능 설명이 아니라 구현 현황이므로 5절로 옮기는 편이 좋습니다. 차량 특화 4가지 중 2번(조명)은 W1에 따라 수정이 필요합니다.
- **4. 주요 사용 시나리오**: 3개 모두 구체적이고 좋습니다. 다만 ①은 조명 정책과, ②는 내기순환·휴게소 거리와 어긋납니다. ③은 "목적지 없이 출발"이라 F4가 동작하지 않는다는 점을 함께 쓰면 오히려 설득력이 생깁니다.
- **5. 개발 계획**: 가장 길고 내부 메모 성격이 강합니다("문서에서 확인", "답 전까지"). 구현 현황 문단을 "완료 / 시뮬레이션 / 예정" 3단 표로 바꿉니다.
- **6. 기대효과 및 발전 가능성**: "(가정치, 근거 보강 필요)"라는 내부 메모가 노출돼 있습니다. 수익 모델에 단가·우선순위·첫 파트너 가설이 없습니다. 확장 계획의 "카메라·ADAS API가 열리면"은 통제할 수 없는 조건이므로 1개로 줄입니다.
- **7. 참고자료**: 체크박스(`[ ]`)가 그대로 남아 있습니다. 제출본에는 실제 링크(영상 URL, GitHub URL, `apk/` 경로)만 적어야 합니다. APK 파일명이 기획서 `apk/팀명_무드라이브_release.apk`와 README `영문팀명_MooDrive_release.apk`로 서로 다르므로 규정(`팀명_앱이름_release.apk`)에 맞춰 하나로 통일합니다.
- **8. 숏폼 링크**: 링크 없이 아이디어만 있습니다. 규정은 세로 30초~1분 영상이고 "차량 내·외부 이미지 노출 최소화"를 요구합니다. 그런데 "같은 길을 맑은 날·비 오는 날 분할 화면"으로 찍으려면 실제 도로와 차량 촬영이 필요해 규정과 충돌하고, 두 날씨를 모두 기다려야 해서 일정 위험도 큽니다. 에뮬레이터 화면과 실내 조명 시각화 패널로 구성한 Spot → Solve → Scene 안으로 바꾸고, 배경 음원 저작권(로열티프리 사용)도 적어 둡니다.
- **머리말**: "v0.1 → v0.2", "근거 원문: `docs/research/...` (각주 번호 동일)"은 내부 메모입니다. 제출본에서 지웁니다.
- 제출 전 "원문 재확인 필요" 표시가 붙은 수치(근거 문서)를 실제 원문으로 확인했다는 기록을 남깁니다. 기획서 마지막 줄의 안내문은 지웁니다.

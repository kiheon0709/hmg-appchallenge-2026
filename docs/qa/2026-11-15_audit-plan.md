## 0. 점검 방법

### 증거를 모으는 법

| 무엇 | 어떻게 |
| --- | --- |
| 화면 | `adb exec-out screencap -p > docs/qa/shots/<번호>_<이름>.png` |
| 앱 로그 | `adb logcat -s SideSeatMeasure SideSeat`. 모드 전환 `app mode A -> B`, 훈련 단계 `app training …`, 단계 완료 `app step done …`, 말 `app say p=… '…'`, 코치 `app coach say rule=…`, 리뷰 `app review summary …`, 조명 `app ambient … ok=…`, 추천 `app route recommend …` |
| 효과음 재생 | 로그 `sfx play name=<이름> loop=…`(재생 요청 성공), 실패는 `sfx focus denied`·`sfx play failed`·`sfx unknown name`. 기기 쪽은 `adb shell dumpsys audio`(포커스 보유자, 재생 중인 player, 스트림 볼륨·음소거)와 `dumpsys media.audio_flinger`(활성 트랙) |
| 음성 안내(TTS) | 로그 `tts speak chars=…` → `tts start` → `tts done`. 실패는 `tts not ready, dropped item`, `tts focus denied`, `tts error=`, `tts watchdog timeout`. 기기 쪽은 `dumpsys audio`의 포커스·player 기록 |
| 음성 인식(STT) | 로그 `stt initialized`, `app heard kind=… source=… '…'`, `stt error=` |
| 호출어 | 로그 `wake start words=…`, `wake …`, `wake back off`, 확인음 `sfx play name=wake` |

소리는 "재생 요청이 나갔고 기기 오디오 계층에서 재생이 잡혔다"까지만 확인해요. 실제로 들리는 음질·크기·말투의 자연스러움은 판단하지 못해요. 보고서에 그렇게 구분해 적어요. 맥의 음소거·볼륨은 건드리지 않아요.

### 확인이 필요한 전제

- release 빌드는 R8이 적용돼 있어요. 위 로그가 release에서도 남는지 2단계 첫 순서로 확인해요. 안 남으면 소리·단계 증거는 `dumpsys`와 화면 캡처로 대신하고, 같은 조작을 debug 빌드에서 로그로 한 번 더 확인해요(그 경우 "debug에서 확인"이라고 적어요).
- release에는 디버그 명령(`am broadcast -a io.moodlab.sideseat.DEBUG`)과 디버그 패널이 없어요. release 점검은 화면 터치(`adb shell input tap`)와 Virtual Console만 써요.
- debug 빌드 전용 도구: `route <이름,…>`(가짜 경로), `scene_day`, `scene_place`, `inject`, `answer`, `ask_pcm`, `wake_pcm`. release에서 조건을 만들 수 없는 항목(내비 경로 추천, 낮·밤 장면 고정, 마이크 질문)에만 쓰고, 썼다고 적어요.
- 낮·밤 장면은 기기 시계(와 위치의 일출·일몰)를 따라요. 장면 시간대는 debug의 `scene_day`로, release에서는 에뮬레이터 시계를 바꿀 수 있으면 바꿔서 봐요(에뮬레이터 안의 설정만, 맥 설정은 아님).
- 주간·야간 UI 테마는 시스템 다크 모드를 따라요(`adb shell cmd uimode night yes|no`).
- 세로 창(835×1210)을 만드는 방법은 README에 없어요. 에뮬레이터의 창 배치 기능이나 `wm size`로 시도하고, 안 되면 확인 불가로 적어요.
- 앞차 급정거는 1.5초 안에 Virtual Console의 BRAKE를 눌러야 해요. 브라우저 조작 지연으로 사람이 하기 어려우면 Virtual Console의 HTTP 요청을 스크립트로 보내요.

## 3. 소스를 읽으며 생긴 의문 (2단계에서 사실 확인)

판정이 아니라 확인할 거리예요. 실제로 돌려 보고 맞는지 틀리는지 적어요.

1. README는 "장소와 시간대(낮·해 질 녘·밤)가 바뀐다"고 하지만, 폭우·터널·맞은편 차·안개·졸음은 항상 밤으로 그려요. C1·C2 챕터는 낮에 해도 거의 밤 장면일 수 있어요.
2. 효과음 파일 `wiper`, `wind`, `chime`, `tick`은 앱 코드 어디에서도 재생을 부르지 않아요. 폭우에서 와이퍼 소리가 없을 수 있어요.
3. 말로 답하는 문제(고장·하이패스)는 정답이 전부 1번 보기예요. 두 번째 판부터는 읽지 않고 맞힐 수 있어요.
4. 리뷰의 "지금 1분만 연습할까요?"는 교관 대결 경로로 상황을 던져요. 끝난 뒤 결과 화면 없이 교관 대결 화면에 남을 수 있어요.
5. 내리기 전(C4)은 시간 제한이 없어 조작하지 않으면 끝나지 않아요.
6. 주행 시간이 분 단위 내림이라 짧은 시험 주행은 "0분"으로 보여요.
7. 지난 주행의 추천 이유("지난 주행에서 ○○ 상황이 있었어요.")는 다음 주행 전까지 계속 남아요. 그 상황을 연습한 뒤에도 같은 추천이 뜰 수 있어요.
8. "이 차 면허"는 사용자가 고른 차종이 아니라 차량 신호의 차종 키로 나눠 세요. 차종을 바꿔도 면허 진행이 그대로일 수 있어요.
9. 훈련 화면에서 Back 키는 "그만하기"와 다른 경로예요(L8).
10. 즉시 안전 규칙(K01·K02 등)은 "30분에 최대 3번" 제한을 받지 않아요. README 문구와 다를 수 있어요.
11. 교관 대결은 시작할 때 음성 안내가 없어요.
12. `core/src/main/resources/catalog/tracks.json`(음악 60여 곡 목록)은 지금 앱 기능과 관련이 없어 보여요. APK에 들어가는지 확인해요.
13. 앞차 급정거는 1.5초가 지나면 실패예요. Virtual Console 조작으로는 통과가 매우 어려울 수 있고, 실차에서는 발이 페달에 있어야 해요.

## 4. 범위에서 뺀 것과 이름 변경

- UI/UX·디자인 평가(글자 크기·대비, 정렬·여백, 문구의 자연스러움, 장면의 사실감)는 별도 세션(ux-review)이 맡아요. 이 점검은 기능과 동작만 봐요. 다만 기능이 화면에 안 보이거나, 잘리거나, 눌리지 않는 문제는 기능 문제로 적어요.
- 앱 이름이 "옆자리"에서 "타비(TABI)"로 바뀌는 중이에요. 이 점검표의 기대 문구는 1단계에 읽은 소스(옛 이름) 기준이에요. 2단계에서는 최종 빌드를 기준으로 보고, 이름이 섞여 보이는 것은 실패로 세지 않고 "아직 옛 이름이 남은 곳" 목록으로만 적어요(화면 글자, 음성, 알림, 앱 목록 이름).
